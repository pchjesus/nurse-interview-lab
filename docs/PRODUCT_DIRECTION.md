# Nurse Interview Lab — 제품 방향 및 단계별 개발 지침

> 상태: **채택한 제품 방향 / 기능 구현 지시가 아님**  
> 기준일: 2026-11-04  
> 적용 대상: Nurse Interview Lab의 신규 설계·Codex 작업 지시·검증  
> 코드 작업 원칙은 저장소 루트의 [AGENTS.md](../AGENTS.md)를 함께 따른다.

## 1. 목적과 성공 기준

Nurse Interview Lab은 **학생들이 서로 진행한 간호사 모의면접의 답변을 다시 확인하고, 간호학적 오류와 부족한 부분을 근거와 함께 정리해 복습하는 설치 없는 웹앱**이다.

기존의 모의면접과 동료 피드백을 대체하지 않는다. 면접 도중 지적했지만 잊어버린 내용, 놓친 오류, 다시 찾아봐야 할 교재 부분을 기록하고 개인별 PDF로 보존하는 것이 핵심이다.

**첫 번째 완성품의 성공 기준:**

1. 학생이 웹사이트에 접속한다(별도 프로그램 설치, 계정 연동, API 키 불필요).
2. CLOVA Note에서 전사한 **텍스트를 복사해 붙여넣는다**. TXT 지원을 우선 검토하고, 텍스트 선택 가능한 PDF 가져오기는 후속 기능으로 둔다.
3. 질문·화자·실제 답변을 확인하거나 수정한다.
4. 웹앱이 전사본과 제공 가능한 평가 기준을 바탕으로 ChatGPT용 분석 프롬프트를 구성한다.
5. 학생 본인의 AI 서비스에서 평가한 결과를 **JSON 1.1 텍스트로 복사해 웹앱에 붙여넣거나 파일로 가져온다**.
6. 보고서 검증·미리보기 후 임시 관리하고, 개인별 PDF/전체 백업을 본인 기기에 저장한다.

외부 ChatGPT 이동과 복사·붙여넣기는 초기 버전의 **명시적인 절충점**이다. 이를 숨기거나 '웹앱 자동 AI 평가'로 표현하지 않는다. 절차는 화면 안내·복사 버튼·붙여넣기 입력창으로 최대한 단순화한다. 사용자 테스트로 불편 정도를 검증한다.

## 2. 기능별 역할과 경계

| 도구 | 담당 | 당분간 하지 않는 일 |
| --- | --- | --- |
| CLOVA Note | 기존 녹음의 전사·화자 구분 | 웹앱 자체 녹음 전사 API |
| 학생의 AI 계정(예: ChatGPT) | 전사본과 **실제로 제공된** 평가 기준을 바탕으로 검토·분석 | 앱이 학생의 ChatGPT 계정/구독 사용량을 API로 자동 호출 |
| Nurse Interview Lab | 전사 입력 안내, 구조 확인, 분석 요청문 준비, 결과 JSON 검증, 보고서·PDF·패키지·로컬 보관 | 무단 업로드, 자체 AI 판정인 것처럼 표시, 중앙 서버 보관 |
| 사람이 확인한 교재·지침·기출 | 평가 기준, 오류 검토, 케이스·질문은행의 근거 | 존재하지 않는 페이지·인용 자동 생성 |

AI가 분석한 결과는 **학습 보조 피드백**이다. 임상적 정답, 병원 공식 평가 또는 합격 예측으로 표현하지 않는다.

## 3. 임상 정확성·평가 규칙

- **실제 학생 발언**, **동료/AI의 해석**, **검증된 근거**, **확인 필요**, **제안 답변**을 구분한다.
- 잘못 말했다는 판단, 질문 범위에 비추어 누락된 내용, 언급하지 않았지만 필수라고 단정할 수 없는 내용을 별도로 구분한다.
- 직무면접: 정확성, 우선순위, 적절한 사정·중재, 위험한 오개념과 근거를 평가한다.
- 인성면접: 질문 적합성, 논리, 구체성, 전문직 태도, 의사소통을 평가한다. 객관적 의료 정답과 같은 방식으로 채점하지 않는다.
- 질환·감염·약물 등 위험성이 높은 항목은 AI 판단만으로 확정하지 않는다. 확인하지 못하면 **미검증·교재 재확인 필요**를 표시한다.
- 실제 자료로 확인된 서지만 APA 7판으로 표기한다. 저자, 판, 연도, 페이지, 병원 인재상 등을 임의로 만들지 않는다.
- 출처 검증 여부는 앱이 독립적으로 교재와 대조했다는 뜻이 아님을 안내한다.

## 4. 레퍼런스·질문은행의 단계적 도입

레퍼런스 **전체를 먼저 구축할 필요는 없다**. 첫 번째 완성품은 등록하지 않은 질문도 처리할 수 있어야 한다.

단계적으로 다음을 구조화한다.
- 출처 서지정보와 실제 확인 범위, 확인 상태
- 질문의 영역(직무/인성), 관련 핵심 간호지식
- 필수 확인 요소, 흔한 오류, 추가 학습 항목
- 실제 확인한 교재·지침 및 페이지 연결
- 검증된 질문은행과 가상 케이스

교재·기출자료는 사용자에게 제공된 범위와 저작권·이용허락을 지키며 활용한다. **저작권이 있는 원문 PDF를 공개 GitHub에 올리거나 웹앱 정적 자산에 무단 포함하지 않는다.** 직접 작성·검증한 평가 기준을 우선한다.

웹앱이 ChatGPT용 프롬프트를 만들 때는 **실제로 접근 가능한 평가 기준만** 포함한다. 서지정보만 등록된 교재를 AI가 읽은 것처럼 표현하지 않는다.

## 5. 저장·비용·개인정보

- 기본 아키텍처: **GitHub Pages + React/TypeScript/Vite + 개인 브라우저 IndexedDB + JSON 백업 + 로컬 PDF 생성**.
- 사용자는 자기 기록만 관리한다. 중앙 80인 사용자 DB, 로그인, 동기화, AI 사용료를 개발자가 부담하는 구조는 현재 목표가 아니다.
- 현재 운영판의 **기본 메모리 저장** 및 사용자 명시 동의를 통한 IndexedDB 저장 방식을 정확히 안내한다. 이를 이미 구현된 자동 임시 저장·만료 기능으로 혼동하지 않는다.
- 기존 Supabase B1~B4-C 개발 브랜치와 Draft PR은 **보존하되 개발·활성화는 동결**한다. 실제 DB SQL, OTP 계정/메일, 서버 업로드, 서버 연동은 사용자의 새 승인 없이는 실행하지 않는다.
- 로컬 기록도 브라우저 삭제·장치 변경·저장 실패 시 사라질 수 있다. PDF 외에도 **복원이 가능한 JSON 백업**을 안내한다. PDF는 사람이 읽을 결과물이며 JSON 전체 백업을 대체하지 않는다.
- 복수의 GitHub Pages 프로젝트가 같은 `github.io` 호스트를 공유할 수 있으므로 브라우저 origin 격리·개인정보 위험을 후속 보안 검토에 포함한다.
- 학생 녹음·전사 및 AI 외부 전송 전 참여자 동의, 가명화, 최소 수집을 안내한다. 실제 개인정보·교재 원문을 저장소, 테스트, CI, 로그에 올리지 않는다.

### 예정된 임시 보관·자동 정리

- 기록별 보관 기간 설정, 만료 알림, 삭제 관리 기능은 **미구현/후속 계획**이다.
- 브라우저가 닫혀 있으면 지정 시각 정확히 삭제할 수 없다. 다음 앱 실행 시 만료 여부를 확인하는 설계를 우선 검토한다.
- 데이터 삭제가 다운로드 요청만을 근거로 자동 확정되지 않도록 한다. 내보내기 안내·사용자 확인·복원 가능한 백업을 우선한다.
- 서버 또는 브라우저가 데이터를 영구 보존한다고 약속하지 않는다.

## 6. 결과 PDF·통합 답변 패키지

- **현재 구현:** 개별 참가자/전체 면접의 평가 PDF 및 전체 JSON 백업.
- **후속:** 여러 평가 기록 선택 → 표지·목차·실제 답변·근거·개선사항을 하나의 PDF로 생성.
- **그다음:** 이미 내보낸 PDF 여러 개의 브라우저 내 병합 및 정리.
- 원본 발언과 제안 답변을 구분하고, 출처 미검증 상태를 PDF에도 유지한다.
- 패키지 생성이 성공했다고 원본을 자동 삭제하지 않는다. 삭제는 별도 안전 절차로 구현한다.

## 7. 미래의 가상면접 — 기존 흐름 재사용

검증된 질문·케이스를 제시하고 **직접 입력**, **녹음→CLOVA Note 전사**, **평가 프롬프트**, **자가 평가** 중 편한 방식을 허용한다.

실제 모의면접과 동일한 구조로 질문 → 답변 → 근거 비교 → 피드백 → 개인 PDF를 재사용한다. 케이스의 의료적 정확성과 출처를 먼저 검증하며, 초기 버전에서 새로운 LLM·음성 API·서버를 구축하지 않는다.

## 8. 단계별 로드맵(임시 작업명)

- **L0: 제품 방향 정렬** — 이 문서와 AGENTS.md 확정, Supabase 작업 동결, 기존 기능·호환성 검증.
- **L1: 완주 가능한 평가 흐름** — CLOVA 텍스트 복붙 → 질문/화자 확인 → 분석 프롬프트 복사 → JSON 결과 붙여넣기/검증 → 개인 PDF.
- **L2: 개인 기록 안전성** — 저장 상태·오류 안내, 임시 보관·백업·복원·안전한 만료·삭제 정책.
- **L3: 복습 경험** — 다중 보고서 PDF 패키지, 탐색·정렬·복습 관리.
- **L4: 근거 시스템** — 실제 확인한 출처·평가 기준 카드를 소량부터 추가.
- **L5: 가상면접** — 검증된 질문은행·케이스, 입력 방식 선택, 기존 평가 흐름 재사용.
- **장기 검토:** 브라우저 AI, 외부 평가 API, 자체 전사, 중앙 동기화는 **별도 비용·개인정보·성능 검증 및 명시적 승인 후**에만 추진.

버전 번호(v0.6 등)는 기존의 동결된 서버 브랜치와 혼동하지 않도록 기능 계획에 붙이지 않는다. 사용 가능한 첫 완성품과 사용자 검증을 우선한다.

## 9. 사용자 경험 기준

- **기본 사용자: 프로그래밍·JSON·API를 모르는 학생**. 설치·API 키·개인 계정 연결 없이 웹 진입을 기본으로 한다.
- 메인 흐름은 '전사본 입력 → 평가 요청 준비 → 평가 결과 등록 → PDF 저장'으로 명확히 구성한다.
- 기능 상태를 **현재 가능 / 외부 AI 작업 필요 / 계획 중**으로 명확히 표시한다.
- PC·모바일, 사용법 안내, 가상 데이터 연습을 유지한다.
- 실패·충돌·저장 상태와 복원 경로를 이해하기 쉬운 한국어로 제공한다.
- 학생 5~10명 파일럿 후 실제 막힘·완주율·평가 근거 이해도를 개선하고, 검증 후 최대 약 80명 이용을 검토한다.

## 10. 코드 작업·검증·승인

1. 작업 시작 전에 최신 GitHub main, 관련 개발 브랜치/PR, 변경 커밋, CI를 확인한다.
2. Codex의 완료 보고를 그대로 믿지 않고 실제 diff, 코드, 테스트/CI 로그로 확인한다.
3. 변경은 작게 구분해 한 단계 검증 후 다음 작업으로 진행한다.
4. **기존 JSON 1.0/1.1, 전체 백업 1.0, PDF, IndexedDB, 설명서, 가상 연습**의 호환성을 유지한다.
5. 기존 코드·원격에서 확인되지 않는 로컬 작업은 '미확인'으로 기록한다.
6. main 병합, 운영 배포, 실제 데이터 이전/삭제, 서버 활성화는 사용자 명시적 승인이 필요하다.
7. US Stock Lab의 Supabase 프로젝트·설정·데이터는 접근·수정하지 않는다.
