# 서버 저장 기반 설계 (미연결)

공식 Supabase SDK는 설치되어 있지만 앱 시작 시 클라이언트를 만들지 않습니다. 이메일 OTP 인증 화면이 있으며 명시적 코드 요청 시 전용 인증 서버에만 접근합니다. 서버 데이터 저장·동기화 및 데이터 이전 버튼은 없습니다. 앱은 기기 전용이며 기존 IndexedDB와 JSON 백업이 원본입니다. Nurse Interview Lab 전용 Supabase 프로젝트와 운영 환경이 준비·검증되기 전에는 실제 개인정보 동기화를 활성화하지 않습니다. US Stock Lab의 프로젝트, 인증, 데이터, 설정은 사용하지 않습니다.

## 비활성 SDK 설정

사용자가 제공한 전용 프로젝트 정보는 `nurse-interview-lab`, project ID `aevhsdqrirgslfetknip`, region `ap-northeast-2`입니다. 이 정보는 실제 프로젝트 연결이나 접근 권한을 검증한 결과가 아닙니다. 로컬 개발 시 `.env.example`을 `.env.local`로 복사하고 해당 전용 프로젝트 대시보드에서 **publishable 공개 키**를 확인해 입력합니다. `VITE_SUPABASE_URL`은 해당 프로젝트 HTTPS URL이어야 하며 `VITE_SUPABASE_PUBLISHABLE_KEY`에는 `sb_publishable_` 공개 키만 허용합니다. 누락 또는 잘못된 값은 로컬 앱을 중단하지 않습니다. 별도 프로젝트를 추가하거나 교체할 경우 명시적 검토와 설정 코드 변경이 필요합니다.

Vite의 `VITE_` 값은 클라이언트에 노출될 수 있습니다. 공개 키도 접근 제어 수단이 아니며 RLS가 필수입니다. `service_role`, `sb_secret_`, 비밀번호, 액세스 토큰 등 비밀은 `.env.example`, 브라우저 번들, 저장소에 넣지 않습니다. `.env.local`은 Git에서 제외됩니다. 값의 정합성 검증은 프로젝트 존재·권한·RLS를 확인하지 않습니다.

`src/cloud/supabase.ts`의 팩토리는 명시적으로 호출될 때만 SDK를 불러와 클라이언트를 생성합니다. 자동 인증 초기화, 세션 지속, URL 세션 감지, 토큰 자동 갱신을 끄며 기존 비활성 팩토리의 HTTP fetch는 차단됩니다. 별도의 OTP 팩토리는 명시적 로그인 요청 시에만 생성되며 OTP·검증·로그아웃 외 HTTP 경로는 차단합니다. 면접 데이터 전송·동기화는 제공하지 않습니다. 이 비활성 구성은 향후 `CloudTransport` 구현을 위한 시작점일 뿐 RLS나 서버 권한을 대신하지 않습니다. SDK는 `@supabase/supabase-js` 2.118.0, Node.js 22 이상을 사용합니다.

## GitHub 연결 시 주의

Supabase GitHub 연동의 설정에 따라 브랜치 연결, 프리뷰 브랜치 생성 또는 마이그레이션 실행이 발생할 수 있습니다. 이번 단계에서는 연동·마이그레이션을 실행하지 않습니다. 향후 연결 전에 대상 프로젝트 ID와 브랜치, 자동 마이그레이션 설정·권한·실행 조건을 검토하고, US Stock Lab 프로젝트가 선택되지 않았는지 확인하세요. 실제 스키마나 RLS 변경은 별도 검토와 승인된 절차에서만 수행합니다.

## 데이터와 저장 계약

서버의 사용자별 단일 백업은 인증 주체의 소유자 ID, `formatVersion` (`1.0` 전체 백업), 서버가 발급하는 양의 정수 `revision`, 서버 갱신 시각, 전체 백업 JSON을 포함합니다. 기기 데이터와 서버 데이터는 별개이며, 동기화 성공은 서버 응답과 재조회가 모두 요청의 소유자·버전·내용과 일치할 때만 표시합니다. 재조회 실패나 네트워크 단절은 결과 미확정으로 표시하고 자동 재전송하지 않습니다. 서버 장애에도 기기 데이터를 삭제하지 않으며 사용자가 전체 JSON 백업을 별도로 보관합니다.

`CloudTransport`는 인증 세션에 묶인 전송 경계입니다. 실제 구현은 전달된 예상 소유자와 인증 토큰의 주체가 일치하는지 확인하고 동일 세션의 토큰으로 요청해야 합니다. **클라이언트의 소유자 확인은 접근 제어가 아닙니다.** 서버는 토큰을 검증하고 인증된 주체로 범위를 결정해야 합니다. 변경은 서버에서 원자적으로 `expectedRevision`과 현재 값을 비교해 수행합니다. 최초 생성은 행이 없을 때만 허용하고, 기존 행은 버전이 일치할 때만 수정하여 새 버전을 발급합니다. 경쟁·중복·삭제·재생성 시 기존 기록을 덮어쓰지 않고 충돌로 처리해야 합니다. 마지막 저장 우선 처리나 자동 병합은 사용하지 않습니다.

기기→서버 이전은 명시적인 사용자 승인 전에 대상 사람·보고서 개수와 서버 기존 데이터 유무를 보여 줍니다. 서버에 데이터가 있거나 미리보기 후 기기 데이터·계정이 바뀌면 중단합니다. 승인 이후에도 최초 생성 조건으로 서버에서 원자적으로 비교합니다. 실패·미확정 시 기기 데이터를 변경하지 않으며 백업을 유지합니다. 이 저장 계약은 현재 테스트용 주입 경계일 뿐 실제 연결이나 이전을 수행하지 않습니다.

## 인증과 RLS 계획

이메일 OTP를 구현했으며 매직링크는 사용하지 않습니다. 실제 전달과 세션 검증은 아직 수행하지 않았습니다. 인증 제공자·이메일 템플릿·만료 설정은 [이메일 OTP 안내](EMAIL_OTP_AUTH.md)를 확인하세요. 향후 로그인 구현 시 승인된 실제 앱 출처와 정확한 경로만 인증 리다이렉트로 등록하고, 만료·재사용·계정 전환과 공개키·RLS를 검증합니다. 동기화는 사용자 동의, 충돌 확인과 재조회 확인 이후 별도 단계에서 활성화합니다. 공개 클라이언트 키만 브라우저에 사용하며 service-role 키, 데이터베이스 비밀번호 등 관리용 비밀은 프런트엔드나 저장소에 두지 않습니다.

실제 스키마 적용 시 사용자별 고유 소유자 키를 인증 사용자 ID에 묶고 RLS를 강제합니다. 읽기·수정·삭제는 인증된 `auth.uid()`가 소유자와 일치할 때만, 생성의 소유자도 인증 주체와 일치할 때만 허용합니다. 비로그인 사용자는 거부합니다. 경쟁 방지를 우회하는 직접 갱신을 허용하지 말고, 서버가 인증 주체를 고정해 버전을 비교하는 원자적 저장 경로와 최소 권한을 설계·검증해야 합니다. 정책 SQL, 마이그레이션, 배포는 실제 전용 프로젝트와 테스트 계정이 준비된 후 별도 검토합니다.

최소 두 개의 서로 다른 테스트 계정과 비로그인 세션으로 타인의 읽기·생성·수정·삭제 거부, 자신의 정상 동작, 인증 만료, 동시 수정 충돌을 실제 프로젝트에서 검증해야 합니다. 로컬 가짜 저장소 테스트는 RLS나 Supabase 인증 검증이 아닙니다. 현재 실제 RLS 정책은 적용되지 않았고 테스트 계정 검증도 수행되지 않았습니다.

## 독립 출처와 운영 전제

GitHub Pages의 같은 출처에 있는 프로젝트는 브라우저 저장소와 스크립트 신뢰 경계를 공유하므로 경로만 달리해도 보안상 격리되지 않습니다. 이번 비활성 SDK 설정 단계에 별도 도메인은 필수 조건이 아닙니다. 실제 개인정보 저장을 활성화하기 전 전용 도메인 또는 별도의 격리된 출처를 우선 검토하고, 불가한 경우 같은 출처의 다른 앱을 포함한 신뢰 경계와 위험을 평가해야 합니다. DNS·TLS·인증 리다이렉트·CSP·배포 권한·공급망·로그 및 백업 수명주기, 접근 정책, 복구 절차도 검토해야 합니다. 공용 또는 검증되지 않은 호스팅에서는 동기화를 켜지 않습니다.

기존 사용자에게는 기기 데이터의 전체 JSON 백업과 복원 방법을 유지합니다. 서버 데이터와 기기 데이터가 충돌하면 어느 쪽도 자동 삭제하지 않습니다. 저장 위치, 기기 저장 상태, 서버 상태와 마지막으로 확인된 동기화 시각은 각각 표시하고, 서버 기능이 비활성인 현재는 연결되지 않음과 동기화 없음으로 표시합니다.
