# 서버 백업 데이터베이스 검토 초안 (v0.6-B2)

이 문서는 별도 승인 전 검토용이다. SQL은 실제 Supabase 프로젝트에 적용하지 않았으며, 현재 앱의 서버 저장·동기화 기능도 활성화하지 않는다. 대상은 전용 프로젝트 `aevhsdqrirgslfetknip`이며 다른 프로젝트의 인증·데이터·설정은 사용하지 않는다. 테스트에는 가상 데이터만 사용한다. PGlite를 이용한 독립 PostgreSQL 호환 검증도 Supabase Auth, PostgREST, 프로젝트별 역할 및 배포 설정의 실제 동작을 증명하지 않는다. PGlite에서 수행한 순차 충돌 검증은 독립 연결의 실제 병렬 경쟁 테스트를 대체하지 않는다.

## 데이터와 저장 계약

인증된 사용자마다 최대 하나의 전체 백업을 저장한다. `owner_id`는 서버가 인증 주체에서 결정하는 UUID이며 `format_version`은 전체 백업 형식 `1.0`, `revision`은 서버가 발급하는 양의 정수, `backup`은 전체 백업 JSON, `updated_at`은 서버에서 정한 시각이다. 백업 내부의 `schemaVersion: "1.0"`과 보고서 자체의 `schemaVersion: "1.0"` 또는 `"1.1"`은 서로 다른 버전이다. 보고서 버전이 1.1이어도 전체 백업 형식은 1.0일 수 있다.

초안은 `public.nurse_backups` 테이블과 `public.save_nurse_backup(p_expected_owner_id, p_expected_revision, p_format_version, p_backup)` 함수를 사용한다. 인증된 역할에는 RLS로 제한된 SELECT와 저장 함수 실행만 허용하고 직접 INSERT·UPDATE·DELETE는 허용하지 않는다. 함수는 `SECURITY DEFINER`로 실행되며 `auth.uid()`를 소유자로 고정하고 요청의 예상 소유자가 일치하는지 검사한다. Supabase 익명 로그인 사용자는 허용하지 않으며 JWT의 `is_anonymous` 값이 명시적으로 false가 아니면 읽기와 쓰기를 거부한다. 실제 프로젝트에서 발급하는 이메일 OTP JWT의 해당 클레임을 검증하기 전까지 활성화하지 않는다. 충돌은 SQLSTATE `P0001`로 반환한다. revision은 JavaScript 안전 정수 상한 `9007199254740991`까지만 허용한다. 계정 삭제의 외래 키는 RESTRICT로 백업의 무심코 연쇄 삭제를 방지한다. 사용자 요청에 따른 안전한 서버 데이터 삭제 및 계정 삭제 절차는 별도 설계가 필요하다.

기존 `CloudRepository`는 `ownerId`, `formatVersion`, `revision`, `updatedAt`, `backup`을 기대한다. 실제 전송 어댑터를 만드는 별도 단계에서 서버의 snake_case를 이 형식으로 변환하고, 요청 전후 세션 주체를 확인해야 한다. 형식·연결 무결성은 클라이언트 `backupSchema`로도 검사한다. DB의 기본 구조 제약만으로 전체 JSON과 임상 내용의 정확성이 검증되는 것은 아니다.

최초 생성의 예상 revision은 null이며 행이 없을 때만 성공한다. 수정은 일치하는 revision 조건으로 단일 원자적 갱신을 수행하며 서버가 revision을 하나 증가시킨다. 동시에 같은 버전을 수정하면 하나만 성공하고 나머지는 충돌이다. 중복 요청도 충돌이며 자동 병합 또는 마지막 저장 우선 처리는 없다. 클라이언트가 직접 테이블을 갱신해 revision 검사를 우회할 수 없어야 한다. 다른 계정의 소유자 ID는 클라이언트가 권한을 얻는 수단이 될 수 없다.

저장 응답이 분실되거나 세션이 변경되면 결과는 **미확정**이다. 자동 재전송하거나 성공으로 표시하지 않는다. 같은 인증 주체로 다시 로그인한 후 서버의 revision과 내용을 조회해 확인하고, 이미 다른 쓰기가 발생했거나 결과를 판단할 수 없다면 사용자에게 충돌을 보여 주고 로컬 백업을 보존한다. 같은 내용이라고 해서 해당 요청이 반드시 성공했다고 단정할 수는 없다. 수정 중 로그아웃·만료·계정 전환이 발생하면 이전 요청의 결과를 새로운 계정에 연결하지 않는다. JWT 만료 이전에 서버가 이미 허용한 요청은 취소할 수 없으므로 결과를 재조회해 확인해야 한다.

## 보안 및 적용 전 검토

인증 주체는 검증된 JWT의 `auth.uid()`만 신뢰한다. 비로그인 요청을 거부하고 본인 행만 조회하도록 RLS를 적용하며, RLS와 별개로 테이블 및 함수에 대한 PUBLIC·anon·authenticated 권한을 점검한다. 사용자에게 직접 쓰기 권한을 주지 않거나 쓰기 경로가 원자적 비교를 강제해야 한다. 테이블 소유자와 BYPASSRLS 역할은 RLS를 우회할 수 있으므로 관리용 키는 클라이언트에 넣지 않는다. `SECURITY DEFINER`가 필요한 경우 고정된 안전한 `search_path`, 스키마 한정 이름, 소유자 권한, PUBLIC 실행 권한 철회, SQL injection 및 권한 상승 여부를 별도로 검토한다. 대안인 invoker 함수는 호출자의 테이블 권한과 RLS로 통제되지만 직접 UPDATE 권한이 있으면 비교를 우회할 수 있어 별도 방어가 필요하다.

동일 GitHub Pages 출처의 다른 프로젝트는 동일한 스크립트·브라우저 저장소 신뢰 경계를 공유한다. 실제 개인정보를 활성화하기 전 별도 출처 또는 동등한 완화책, CSP·배포 권한·공급망과 로그 정책을 검토한다. 인증 상태 UI나 공개 키는 접근 제어가 아니다. 관리자·마이그레이션 역할, 소유권, 기본 권한과 향후 생성 객체의 권한도 대상 프로젝트에서 별도 검토한다.

## 이전 중단 및 복구

이전은 아직 구현하거나 실행하지 않는다. 이후 별도 승인된 단계에서 먼저 전체 JSON을 기기에 백업하고, 사용자에게 사람·보고서 수와 서버 데이터 유무를 보여 준다. 서버에 데이터가 존재하거나 조회 실패, 계정 변경, 로컬 데이터 변경, 형식 검증 실패, 인증 만료 또는 승인이 불명확하면 중단한다. 미리보기 후에도 최초 생성 원자 조건을 재확인한다. 실패나 미확정 결과로 기존 IndexedDB 또는 백업을 삭제하지 않는다.

실제 적용 전에는 대상 프로젝트와 역할, 기존 객체·데이터·정책·함수 및 의존성을 확인한다. 기존 데이터나 같은 이름의 객체가 발견되면 덮어쓰거나 삭제하지 않고 이전 계획을 중단해 별도 검토한다. 변경 전 복구 가능한 백업과 복원 연습을 준비한다. 롤백은 승인된 관리자가 먼저 서버 쓰기를 중지하고 사용자 백업을 보존한 뒤, 해당 변경으로 생성된 객체만 의존성과 데이터 보존을 확인하여 제거하는 별도 작업으로 수행한다. 데이터가 생긴 뒤 테이블을 DROP하는 것은 파괴적이므로 자동 롤백하지 않는다. 적용 도중 장애가 발생하면 백업과 감사 기록을 확인하고, 사용자에게 재시도·동기화를 지시하기 전 데이터 상태를 확인한다.

## 검증 계획

- 일회성 독립 PostgreSQL에서 가상 인증 주체 A·B 및 비로그인 역할을 준비하고, 생성·본인 조회·일치 revision 수정 및 서버 revision 증가를 검사한다.
- 타인 조회, owner 위조 생성, 직접 수정·삭제, RPC 실행 및 비로그인 접근을 테이블 권한과 RLS 양쪽에서 확인한다. 실패가 빈 조회 결과인지 권한 오류인지 구별한다.
- 같은 revision의 병렬 요청 두 개 중 하나만 성공하는지, 최초 생성 경쟁·중복 요청·오래된 수정이 충돌하는지 확인한다.
- 네트워크 실패 후 결과 미확정, 응답 후 다른 쓰기, 인증 만료와 계정 변경 시 자동 재시도가 없고 기기 데이터가 보존되는지 클라이언트 수준에서 검사한다.
- 실제 Supabase에 대한 검증은 별도 승인 후 전용 테스트 환경에서 서로 다른 두 테스트 계정과 비로그인 세션을 사용한다. Supabase의 실제 JWT, RLS·테이블·함수 권한, PostgREST 노출, 네트워크 단절 및 동시성까지 확인하기 전에는 운영 준비가 완료된 것으로 보지 않는다.

### 독립 실행 방법

`tests/sql/run-pglite.mjs`는 외부 DB URL을 받지 않는 메모리 전용 테스트다. 예를 들어 저장소 밖 임시 디렉터리에 `npm install --prefix /tmp/nurse-b2-pg --no-save @electric-sql/pglite@0.5.14`로 설치하고 `node tests/sql/run-pglite.mjs /tmp/nurse-b2-pg`를 실행한다. SQL의 인증 함수는 모의 구현이다.

`tests/sql/run-concurrency.sh`는 별도로 준비한 빈 일회성 PostgreSQL의 `/tmp` 유닉스 소켓과 `nurse_b2_test_`로 시작하는 전용 DB 이름만 허용하며, 실제 동시 생성·수정 두 세션을 검증한다. `psql`과 로컬 서버가 필요하다. PostgreSQL 18.6의 일회성 로컬 서버에서 최초 생성 및 같은 revision 수정의 두 연결 경합을 각각 실행해 성공 1건과 revision 충돌 1건을 확인했다. CI에서도 독립 서버로 두 시험을 실행한다. 실행 전 전용 DB가 비어 있고 폐기 가능한지 확인한다.

함수 소유자와 테이블 소유자의 일치, 고정 search_path, PUBLIC·anon EXECUTE 철회 및 authenticated EXECUTE를 모의 환경에서 검사한다. `auth.role()`은 검증된 JWT의 role을 확인하는 추가 방어이며 실제 Supabase의 토큰과 함수 동작은 별도 검증해야 한다. 실제 적용 전 함수 소유자와 역할 상속·기본 권한을 확인한다.
